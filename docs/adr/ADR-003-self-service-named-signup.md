# ADR-003: Самостоятельная регистрация по имени

Статус: Accepted
Дата: 2026-08-20
Изменяет: пункт 6 ADR-002 и Auth baseline

## Контекст

Ручное создание email/password аккаунтов в Supabase неудобно владельцу и
непонятно ученикам. Группа остаётся маленькой (1–3 человека), но каждый ученик
должен самостоятельно создать учётную запись и получить изолированную историю.

Одного имени без секрета недостаточно: любой человек, знающий имя, смог бы войти
в чужой профиль. Настоящий email продукту не нужен, а восстановление пароля не
входит в MVP.

## Решение

1. В UI использовать имя + пароль длиной от 8 символов.
2. Нормализовать имя (Unicode NFKC, регистр, пробелы) и получать из него
   детерминированный технический email через SHA-256. Email не показывается и не
   является секретом.
3. При signup записывать `display_name` и `username_key` в Auth metadata.
4. Auth trigger атомарно создаёт `profiles` для нового `auth.users.id`.
5. Историю по-прежнему изолировать по JWT `auth.uid()` через RLS.
6. На bootstrap временно разрешить signup и отключить email confirmation. После
   регистрации известных пользователей владелец может закрыть signup.

## Последствия

- владелец не создаёт пользователей вручную;
- ученику не нужен email, но нужен уникальный username и пароль;
- восстановление забытого пароля требует owner-controlled reset и остаётся P1;
- пока signup включён, любой посетитель может создать аккаунт, поэтому окно
  регистрации должно быть коротким;
- publishable key остаётся публичным, а разграничение данных обеспечивает RLS.

## Отклонённые варианты

### Только имя

Отклонено: не обеспечивает аутентификацию и позволяет захватить чужую историю.

### Общий PIN в frontend

Отклонено: любой секрет в GitHub Pages bundle является публичным.

### Ручное создание пользователей

Безопасно для закрытой группы, но отклонено владельцем из-за лишнего
администрирования.
